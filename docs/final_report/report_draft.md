## スライド 2. 要約（1 枚で結論）

- 現行方式を Bedrock（Nova Lite）に移すと、OpenAI 版より【再現率 x.xxx → y.yyy、取りこぼし +n 件】下がった
- 改善版（行為の分類 → 条文はコード）で、**取りこぼし【n 件 → m 件】・誤検知【n → m 件】・言語による再現率の差【a → b】・費用【x → y ドル/投稿】**
- 調整に使っていない投稿（test・追加のデータ）でも【同じ傾向】＝データに合わせすぎていない

## ① 取り組んだ課題と、重点を置いた点・理由（スライド 3）

- 必須の課題 1（誤検知）・課題 2（言語による差）に加え、課題 3（費用）・課題 4（条文の一貫性）・O-3・O-4・O-5・O-1・O-8
- **重点: 取りこぼしを増やさずに誤検知を減らす**。理由: 運営は誤検知は目で除けるが、見逃しには気づけない（発注書 2 の注記）
- **重点 2: 条文の付け方を LLM から外す**。理由: ベースラインの分析で【条文の誤り n 件の多くが「2 段目の選択が候補の 1 位を変えた」もの】だった（→ スライド 5）。同時に呼び出しが 1 回になり費用も下がる

## 目標とする水準と根拠（スライド 4）（発注書 4）

| 観点 | 目標 | 根拠 |
|---|---|---|
| 取りこぼし（最優先） | Bedrock ベースライン**以下**、かつ再現率 **0.941 以上**（OpenAI 版の水準） | 必須要件（M-4）。モデルの差し替えで下がった分を取り戻すことも改善として扱う（発注書 3） |
| 誤検知 | 適合率 **0.80 以上**（OpenAI 版 0.750） | 本番では通知の約 4 割が対応不要（課題 1）。運営の確認の手間を 2 割以上減らす水準 |
| 言語による差 | 主な 6 言語の再現率の最大−最小 **0.09 以下** | 1 言語あたり警告すべき投稿は約 25 件で、1 件の違いで約 0.04 動く。「2 件以内の差」を誤差の範囲とみなす |
| 判定の安定性 | 3 回の判定の一致 **98% 以上** | temperature 0・topK 1 で判定する。OpenAI 版の評価では 3 回とも同じだった（evals/README） |
| 費用 | 1 投稿あたり Bedrock ベースラインの **50% 以下**、OpenAI 版（0.000475 ドル）未満 | 呼び出しを 2 回 → 1 回、静的な部分をキャッシュ |
| 判定時間 | 95 パーセンタイル **3 秒以下** | Slack の 3 秒の応答（R3）。応答と判定を分けるまでは、判定の時間がそのまま効く |

## ② ベースラインの取りこぼし・誤検知の分析（言語別）（スライド 5〜6）

- 表: OpenAI 版（発注書の値）と Bedrock ベースラインの言語別の取りこぼし・誤検知・再現率・適合率【compare.md】
- 図: 言語別の再現率・適合率【recall_by_lang.png・precision_by_lang.png】
- 分析の仕方: `summarize.py` の「間違えた投稿」と「区分ごとの内訳」（category・degree・noise）から、
  - 取りこぼし: どの種類（例: リンクの無い外部グループの勧誘、宗教の勧誘、録画の公開）が、どの言語で落ちたか【】
  - 誤検知: 「ルールの注意」「違反の報告」「可否の質問」のように、**禁止行為に触れているが行っていない**投稿が多いか【】
  - 言語: 同じシナリオで言語によって判定が分かれたもの（言語の間の一致）【分かれたシナリオの一覧】
  - 条文: 2 段目の条文の選択が、1 段目の候補の 1 位を変えた件数【】
- ここから導いた原因（仮説） → スライド 7 の設計につなげる
  1. 「触れている」と「行っている」を区別できていない（誤検知）
  2. 日本語の方針と他の言語の投稿の対応付けが弱い（言語による差）
  3. 条文の選択を LLM に任せると、同じ行為でも条文が揺れる（課題 4）

## ③ 改善した判定方式の設計と考え方（スライド 7〜9）

- 図: 旧（2 段の LLM）と新（1 回の構造化出力＋コードの判断）の流れの比較
- 出力の順番に意味がある: `language → gist_ja（日本語の言い換え）→ stance（立場）→ acts（行為）→ decision`。先に言い換えと立場を書かせることで、
  - 言語によらず日本語の方針と照らせる（原因 2）
  - 「注意・報告・質問」の立場なら acts に入れない（原因 1）
- 条文は `V2_ACT_TO_ARTICLE`（運営の `article_guide.txt` と同じ対応）で付ける。LLM の出力は 20 種の値に制限（JSON スキーマの enum）（原因 3）
- 取りこぼしを避ける合成: モデルの warn・acts・判定の操作・招待リンクの「または」
- O-3: 投稿を投稿から決まるタグで囲む。判定の操作の指示 → 警告
- O-4: 失敗 → 「判定できませんでした」で high 通知（スクリーンショット: Slack の運営チャンネルの通知【】）
- 課題 5: 指数バックオフ＋ジッター、予備のモデル（`common/bedrock_client.py`）
- M-5: `lambda/` に実装し、`DETECTION_MODE=bedrock_v2` で本番の Lambda から使える。テスト 【n】 件（`pytest tests/` の結果のスクリーンショット）

## ⑤ 過学習を避けるための工夫（スライド 13）

- **シナリオ単位の dev/test 分割**（`load_dataset.py`）: 58 シナリオを種類（W・S・JH・X）ごとに層別し、ハッシュの順で半分ずつ。同じシナリオの 6 言語の対訳が dev と test に分かれないので、「dev の言い換え」で test を覚えることがない。dev 177 件・test 177 件
- 方針（プロンプト）の調整は **dev の間違いだけ**を見て行い、test は最後に測る。test の値を見て直したら、その旨を書く
- **調整に一度も使わない追加データ 60 件**（O-1、holdout）。提供のデータに無い種類（有償インタビュー・物品の売買・SNS＋インジェクション・アカウントの共有の告知）と紛らわしい安全な投稿
- 手がかりは**一般的なもの**だけ: 招待リンクのドメインと形（WhatsApp・Telegram・Discord・LINE など）は公開の仕様で、データから学んだものではない。提供のデータで 20 件検出・誤検知 0、追加のデータで誤検知 0（コードだけで測った値）
- 正直に書くこと: プロンプトの「締切後・公式の解答の公開後の議論は当たらない」「異性・独身などを条件に相手を探す」の補足は、データセットの正解の根拠（`note`）を読んで加えた。これらに当たる JH のシナリオは dev と test の両方にあるので、test の JH の結果は「完全に未知」ではない【JH を除いた test の値も併記する】

## ⑥ 残った課題と、本番に取り込むための改善案（スライド 14〜15）

- 残った取りこぼし・誤検知の具体例と原因【】
- 本番への取り込み: CDK のパラメータ `LlmProvider=bedrock`・`DetectionMode=bedrock_v2` だけで切り替わる（既定は今のまま）。まず検証用のワークスペースで並走（判定は記録だけ）→ 運営の判断と照合 → 切り替え
- 既存システムの問題点と改善案（O-8）: 応答と判定を SQS で分け、同時に判定する数で LLM・Notion のレート制限を守る（`system_review.md`）
- 評価の CI（O-5）: PR ごとに追加データで評価し、しきい値（`evals/thresholds.json`）を下回ったら落とす。しきい値は測定値から決めて commit する
- 次の打ち手の候補: 判定の確信が低いときだけ上位のモデル（Nova Pro など）に回す段階的な判定、運営の「対応不要」の記録を使った方針の更新
